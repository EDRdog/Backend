# 003. exactly-once 를 켜지 않고 중복은 알림 단계에서 억제한다

- 날짜: 2026-07-22
- 상태: 채택

## 배경
Kafka Streams 의 기본 처리 보장은 at-least-once 다. 장애나 리밸런스로 오프셋 커밋 전에 재시작하면 같은 이벤트를 다시 처리하고, 같은 판정이 두 번 나올 수 있다.

## 결정
EOS 를 켜지 않는다. 대신 alert-service 와 responder-service 가 쿨다운으로 중복 발송을 억제한다.

| | 값 |
|---|---|
| 억제 키 | 수신 대상 + host + ruleId |
| 억제 창 | 60초 |
| 저장 위치 | 인스턴스 로컬 메모리 |

## 근거
> exactly-once 를 켜는 선택지가 있지만 쓰지 않았다. 트랜잭션 코디네이터가 붙어 처리량이 떨어지고 지연이 늘어난다. **중복 판정 자체가 문제가 아니라 중복 알림이 문제**다. 그쪽에서 막는 편이 싸다.

**로컬 메모리로 충분한 이유**: `alerts` 의 파티션 키가 host 라 같은 host 의 알림은 늘 같은 파티션이고, 컨슈머 그룹 안에서 그 파티션은 한 인스턴스가 맡는다. 그래서 인스턴스를 늘려도 로컬 맵이 성립한다. Redis 를 하나 더 두는 것보다 낫다고 봤다.

**두 가지를 더 신경 썼다**:
- 처리 시점의 현재 시각이 아니라 **알림에 실린 이벤트 시각**으로 판단한다. 현재 시각을 쓰면 같은 입력을 재처리했을 때 결과가 달라진다.
- **발송에 실패하면 쿨다운을 되돌린다.** 실패했는데 쿨다운을 소모하면 그 60초 동안 그 알림이 아예 전달되지 않는다.

## 결과/영향
- 리밸런스 직후나 재시작 직후에는 이전 기록이 없어 알림이 한 번 더 갈 수 있다. 받아들인 비용이다.
- EOS 를 나중에 켜려면 비교 수치가 필요해서 측정 인프라만 따로 넣어 두었다(커밋 `cf595fb`). 켜지는 않았다.
