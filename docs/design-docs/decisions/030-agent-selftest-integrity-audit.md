# 030. 에이전트 자체시험·무결성은 설치가 남긴 기준값과 비교하고, 감사기록은 전용 경로로 서버에 보낸다

- 날짜: 2026-11-11
- 상태: 채택

## 배경

KISA EDR 성능평가(BF-10, BF-11, BF-13)는 에이전트에도 세 가지를 요구한다. 구동 중 주기적으로 또는 관리자 요청으로 자체시험을 하고, 자체와 설정값의 무결성을 검증하고, 주요 감사사건의 감사기록을 만들어 서버로 보내는 것이다. 지금 에이전트에는 셋 다 없다(`docs/security/nis-requirements-review.md` 엔드포인트 4.1, 5.1, 5.2). 이미 있는 `-selftest` 는 센서 대신 가짜 이벤트를 보내 서버까지의 경로를 확인하는 다른 용도다.

## 결정

**1. 이름을 나눈다.** `-selftest` 플래그와 `sensor.SelfTest` 는 그대로 둔다. 새 기능은 `internal/selfcheck` 패키지, `-security-check` 플래그, 감사 사건 `security_check` 와 `integrity_check` 로 부른다.

**2. 자체시험 항목은 에이전트 보안 기능이 동작하는지 본다.** 서버 인증서 고정 설정(`server_pinning`: https 이고 `ca_cert_path` 의 CA 를 읽을 수 있다), 설정 파일 권한(`config_permission`: 그룹·기타 접근 불가), 고정 인증서 권한(`ca_cert_permission`: 그룹·기타 쓰기 불가), 센서 생존(`sensors`: 띄운 센서가 전부 살아 있다). 기동 시에 한 번, 이후 `selfcheck_interval_seconds`(기본 3600)마다 돌린다. 관리자는 엔드포인트에서 `-security-check` 로 한 번 돌려 항목별 결과를 보고 실패가 있으면 종료 코드 1 을 받는다.

**3. 무결성 기준값은 설치 스크립트가 기록한다.** 설치 스크립트가 바이너리와 설정 파일을 놓은 직후 `edrdog-agent -config <설정> -record-baseline` 을 불러 두 파일의 SHA-256 을 설정 파일 옆 `integrity.json` 에 쓴다. 에이전트는 기동 시와 주기마다 자기 실행 파일(`os.Executable`)과 설정 파일을 다시 해시해 비교한다. 기준값 파일이 없거나 깨졌으면 둘 다 실패다(지우는 것이 우회가 되면 안 된다). 통과한 항목의 감사기록 `detail` 에는 현재 해시를 싣는다.

**4. 실패해도 에이전트는 계속 돈다.** 멈추면 그 기기의 수집과 대응이 같이 멈춘다. 대응은 감사기록과 로그에 `failure` 를 남기는 것이다(KISA 4.2 의 통보). 관리자가 서버에서 본다.

**5. 감사기록은 이벤트 채널과 따로 보낸다.** 에이전트가 사건(`agent_start`, `agent_stop`, `agent_enroll`, `sensor_stop`, `security_check`, `integrity_check`, `command_result`)을 메모리 로그(상한 1000건)에 쌓고, 이벤트 전송 주기마다 `POST /api/agent/audit` 로 보낸다. collector 가 node_key 로 푼 tenantId 와 host 를 붙여 api-service `POST /api/internal/audit` 로 넘긴다. 못 넘기면 503 이고, 에이전트는 그 배치를 로그 앞으로 되돌려 다음 주기에 다시 보낸다(적어도 한 번 전달). 계약은 `docs/agent-protocol.md` 5절.

## 근거

**기준값을 어디서 얻나.** 위변조한 사람이 기준값도 같이 바꿀 수 있는지가 기준이다.

| 대안 | 버린 이유 |
|---|---|
| 서버가 기대 해시를 내려준다 | 가장 강하다. 에이전트가 있는 기기를 장악해도 서버의 값은 못 바꾼다. 그러나 릴리스마다 서버에 (판번호, 플랫폼, 아키텍처)별 해시 목록을 넣고 갱신해야 하고, 그 목록을 만들고 내려주는 곳이 이번 묶음 밖이다. 개발 빌드나 소스에서 직접 깐 바이너리는 목록에 없어 항상 실패한다. 설정 파일 해시는 기기마다 달라 이 방식으로 못 푼다. 필요해지면 하트비트 응답에 기대값을 얹어 이 결정 위에 쌓을 수 있다 |
| 첫 기동 때 자기 해시를 기준값으로 저장한다(TOFU) | 첫 기동 전에 이미 바뀐 바이너리를 정상으로 굳힌다. 정당한 교체 때 기준값을 갱신할 경로도 따로 있어야 한다 |
| 릴리스 `.sha256` 을 런타임에 GitHub 에서 받아 대조한다 | 에이전트가 제3자에 접속해야 하고, 오프라인 기기에서 검증이 안 되고, 판번호와 아키텍처로 URL 을 만들어야 한다. 소스에서 직접 깐 빌드는 릴리스에 없다 |
| 바이너리에 자기 해시를 박는다(`-ldflags`) | 자기 자신의 해시를 자기 안에 넣을 수 없다(해시가 바뀌면 값도 바뀐다) |
| 기준값을 설정 파일 안에 넣는다 | 설정 파일의 해시를 설정 파일에 넣을 수 없다(같은 순환) |
| 코드 서명(codesign, Authenticode) | 서명 인증서가 없다. KISA H7 로 따로 보고 있다(`docs/exec-plans/tech-debt.md`) |

**고른 방식이 막는 것과 못 막는 것.** 에이전트는 root 와 SYSTEM 으로 돈다. 그 권한을 가진 사람은 바이너리, 기준값 파일, 에이전트 프로세스를 전부 바꿀 수 있어서, 로컬 비교만으로는 **관리자 권한을 가진 위변조자를 못 막는다.** 잡는 것은 관리자 아닌 쪽의 변경과 사고성 손상(복사 중단, 디스크 오류, 설정 파일을 손으로 고치다 엉킴)이다. 이 한계를 줄이려고 통과한 항목의 현재 SHA-256 을 감사기록 `detail` 에 싣는다. 해시가 서버에 남으므로 관리자가 릴리스 `.sha256` 과 대조할 수 있고, 위변조한 사람이 기록 전송까지 끊으면 주기 기록이 끊긴다는 사실이 증거가 된다. 그 이상(서버가 기대값을 내려주는 것)은 위 표의 첫 줄로 남겨 둔다.

**macOS TCC 와 충돌하지 않는다.** 바이너리를 바꾸면 TCC 권한이 풀리고 enroll 을 새로 탄다(`agent/README.md`). 그래서 정당한 교체는 설치 스크립트를 다시 돌리는 것뿐이고, 그 스크립트가 바이너리와 함께 기준값도 새로 쓴다. 에이전트는 자기를 직접 교체하지 않는다(자체 업데이트가 없다). 사람이 바이너리만 `cp` 로 덮어쓰면 TCC 도 풀리고 무결성 실패도 남는데, 둘 다 맞는 결과다. 기준값 기록은 파일을 읽는 일이라 TCC 와 무관하다.

**감사기록을 이벤트 채널(`type=agent` 이벤트)로 보내지 않은 이유.** `nis-requirements-review.md` 는 가장 작은 방법으로 이것을 제안했다. 그러나 이벤트는 collector 검증, Kafka, detector 입력을 거쳐 ClickHouse 로 가고, 감사기록은 관리자가 조회하는 증적이라 api-service 저장소에 있어야 한다. 이벤트 스키마에 `result` 와 사건 종류를 억지로 넣으면 탐지 입력이 오염된다. collector 의 인증, 본문 상한, 503 재전송은 그대로 재사용하므로 엔드포인트 하나를 더하는 비용만 든다.

**전송 실패 시 메모리 로그에 남겨 재전송한다.** 감사기록은 잃으면 안 되지만 디스크 큐는 이벤트 버퍼처럼 두지 않았다(수동으로 확인할 수 있는 서버 감사기록이 목적이고, 에이전트가 죽으면 이벤트도 같이 사라지는 한계가 이미 있다). 사건 양이 적어(기동 때 몇 건, 주기마다 두 건) 상한 1000건이면 서버가 하루 죽어도 안 넘친다.

**`ts` 가 틀린 단말.** collector 가 0 이하 값을 서버 시각으로 바꾼다. 그 밖의 어긋남은 에이전트 시계를 그대로 기록한다. 감사기록의 목적은 사건이 그 기기에서 언제 있었다고 보고했는지이므로 서버가 임의로 고치지 않는다.

## 결과/영향

- 에이전트: `internal/audit`(기록 로그), `internal/selfcheck`(자체시험, 무결성), 런타임·명령 루프의 훅, `-security-check`, `-record-baseline`, 설정 `selfcheck_interval_seconds`, 설치 스크립트 두 개
- collector: `POST /api/agent/audit`, `AuditClient`
- 에이전트를 collector 보다 나중에 배포한다. 반대면 새 에이전트가 없는 경로로 보낸다(404 가 계속 되돌아와 로그 경고가 쌓인다)
- 기준값이 없는 기존 설치는 무결성이 실패로 기록된다. 설치 스크립트를 다시 돌려야 한다
- 남은 한계(`docs/exec-plans/tech-debt.md`): 관리자 권한 위변조, 서버가 내려주는 기대값, Windows 권한 항목 건너뜀, 서버에서 에이전트에 자체시험을 요청하는 경로, 에이전트가 죽으면 못 보낸 감사기록 소실
