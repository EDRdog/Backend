# 006. 판정은 도착 순서가 아니라 이벤트 발생 시각으로 한다

- 날짜: 2026-07-26
- 상태: 채택

## 배경
가장 심각도가 높은 R2 는 "받아온 파일을 실행" 이라 다운로드와 실행의 **순서**가 성립해야 한다. 그런데 도착 순서가 발생 순서와 같다는 보장이 없다.

- 에이전트는 이벤트를 버퍼에 모아 주기마다 배치로 보낸다. 실패하면 다음 주기에 다시 나간다.
- **macOS 네트워크는 폴링이다.** 연결 시점과 관측 시점 사이에 최대 한 주기의 간격이 있다. 반면 exec 은 커널이 곧바로 밀어 준다.

```
실제로 일어난 순서    [다운로드]  →  [실행]
서버에 도착한 순서    [실행]      →  [다운로드]
```

## 결정
시각을 **Kafka 에 넣기 전, 엔드포인트에서 찍힌 값**으로 쓴다. 상관 버퍼도 이 시각으로 훑고, 새 이벤트보다 앞선 것뿐 아니라 **뒤선 것까지 양쪽으로** 본다.

| 이벤트 | 시각의 출처 |
|---|---|
| 프로세스 / 파일 | 커널이 이벤트에 실어 준 시각 |
| 네트워크 (Windows) | ETW 이벤트의 `TimeCreated` |
| 네트워크 (macOS) | 그 연결을 처음 관측한 스냅샷 시각 (실제보다 최대 한 주기 늦다) |

## 근거
도착 순서로 "다운로드 다음에 실행" 을 찾으면 이 조건은 영영 성립하지 않는다. 실행 이벤트가 먼저 도착하기 때문이다. 실제로 그래서 R2 가 안 잡혔고 커밋 `d65dffe` 로 고쳤다.

**시계가 틀어진 단말**은 버리지 않고 당긴다(`RawEventMapper.MAX_CLOCK_SKEW_MILLIS`). 주석 원문:
> 버리지 않고 당기는 이유는 시계가 틀어진 단말의 이벤트도 판정에는 써야 하기 때문이다. 그냥 두면 detector 의 워터마크가 그 값까지 튀어 다른 이벤트의 상관 버퍼가 통째로 날아간다.

## 결과/영향
- 서버 수신 시각은 판정에 쓰지 않는다. 적재 시각(`ingested_at`)은 별도 컬럼이다.
- macOS 네트워크는 폴링 주기 사이에 열렸다 닫힌 연결을 놓친다. 알려진 한계로 안고 간다.
