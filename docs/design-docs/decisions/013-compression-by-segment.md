# 013. 배치를 먼저 모으고, 구간마다 다른 압축을 쓴다

- 날짜: 2026-08-20
- 상태: 채택

## 배경
`AgentService.publish()` 가 이벤트 한 건마다 `producer.publish()` 를 불렀다. 이 상태에서 압축만 켜면 작은 레코드를 하나씩 압축해 압축률이 나쁘고 압축 헤더 오버헤드만 붙는다.

## 결정
순서가 있는 세 단계다.

1. **발행을 배치로 모은다** (`fb53478`). 압축보다 먼저.
2. **Kafka 발행은 zstd** (`4cc8949`).
3. **에이전트 → collector 구간은 gzip** (`5ba3f22`). 서버가 요청 본문을 풀어서 받는다.

## 근거
**zstd 가 gzip 보다 큰데도 zstd 인 이유**:
> 같은 배치에서 gzip 이 11,302 바이트로 1KB 더 줄었다. 그래도 zstd 를 쓴다. detector 가 Kafka Streams 로 상시 소비해 해제 CPU 가 계속 드는데 그쪽이 zstd 가 훨씬 싸다. 1KB 차이는 그 상시 비용에 비할 것이 못 된다.

**순서가 결정이다**: 500건 배치에서 78.9% 감소였지만, 건당 발행 상태에서 같은 줄만 켰으면 **4.3% 증가**였다. 압축 헤더만 붙기 때문이다.

**에이전트 구간만 gzip 인 이유**:
> 에이전트 → collector 는 고객사 네트워크를 타는 유일한 구간인데 압축이 없다. 나머지 구간은 전부 클러스터 내부라 대역폭이 사실상 공짜다.

**압축 레벨은 기본값**:
> BestCompression 은 CPU 를 훨씬 더 쓰고 이득은 몇 %인데, EDR 에이전트가 고객 단말 CPU 를 먹는 것 자체가 문제라 여기선 기본이 맞다.

**1KB 미만은 압축하지 않는다**(`gzipMinBytes = 1024`): gzip 헤더·트레일러만 18바이트라 수백 바이트짜리 enroll·heartbeat 는 압축하면 오히려 커진다.

**서버 측 해제에 8MB 상한을 둔다**: 다른 항목은 성능 얘기지만 이건 가용성 문제다. 상한 없이 열면 인증된 에이전트 하나로 collector 를 죽일 수 있다.

**넣지 않은 것**: `gzip.Writer` 재사용(`sync.Pool`). 전송 주기가 초 단위라 할당이 병목이 아니다.

## 결과/영향
- 측정값(업링크 87.1% 감소를 8ms 로 샀다)은 측정 조건과 함께 봐야 한다.
- Protobuf 전환과 압축은 상충하지 않는다. Protobuf 는 필드명을 없애고 압축은 남은 반복을 줄인다.

## CPU 측정 (2026-10-16 추가)
처음 결정은 바이트만 쟀고 zstd 의 해제 CPU 이점은 추론이었다. 그래서 따로 쟀다.

**조건**: Apple M4 Pro 12코어 노트북, 단일 스레드 마이크로벤치. 실제 `event.Factory` 로 만든 macOS 형태의 합성 이벤트를 썼다(process·network·file·dns 를 고르게 섞고 시드를 고정). 업링크는 Go 1.26 에서 실제 `compress()` 로, Kafka 는 kafka-clients `MemoryRecordsBuilder` 에 `RawEventMapper` 가 만든 protobuf 를 넣어 쟀다(JDK 23). 각 3회씩 돌린 중앙값이다. 운영 실측은 아니다.

**업링크 (gzip 기본 레벨, JSON 본문)**

| 배치 | 원본 B | gzip B | 감소 | 직렬화 µs | gzip µs |
|---|---|---|---|---|---|
| 1 | 301 | 압축 안 함(1KB 미만) | 0% | 0.4 | 0 |
| 10 | 2,602 | 740 | 71.6% | 3.2 | 93 |
| 50 | 11,600 | 1,850 | 84.1% | 14.8 | 99 |
| 100 | 23,232 | 3,126 | 86.5% | 29.4 | 136 |
| 500 | 111,856 | 12,125 | 89.2% | 143 | 653 |

- 500건 감소율 89.2% 는 운영 87.1%(28분 창)와 같은 범위다.
- 레벨: 500건에서 BestCompression 은 5% 더 줄이고 CPU 를 2.1배 쓴다(1,355µs). BestSpeed 는 CPU 를 0.4배 쓰지만 32% 더 크다. 기본 레벨을 유지한다.
- 에이전트 상한 초당 100건 기준 압축 CPU 는 초당 약 0.13ms, 1코어의 0.02% 미만이다.

**Kafka (500건 한 배치, protobuf)**

| 코덱 | 바이트 | 감소 | 압축 µs | 해제 µs |
|---|---|---|---|---|
| none | 91,477 | 0% | 50 | 13 |
| gzip | 15,636 | 82.9% | 769 | 94 |
| zstd | 15,625 | 82.9% | 134 | 62 |
| lz4 | 25,403 | 72.2% | 83 | 45 |
| snappy | 25,505 | 72.1% | 75 | 37 |

- 이번 데이터에서는 gzip 과 zstd 의 압축률이 같았다. 그런데 zstd 는 압축이 5.7배, 해제가 1.5배 빨랐다. 처음 결정 때의 근거(gzip 이 1KB 더 줄어도 해제가 싸서 zstd)보다 더 강한 근거다.
- lz4·snappy 는 더 싸지만 10%p 덜 줄인다. 이 구간은 클러스터 내부라 대역폭보다 브로커 디스크와 보존량에 걸린다. 그래서 같은 CPU 대에서 더 많이 줄이는 zstd 를 쓴다.
- 압축이 늘린 CPU 는 건당 0.17µs(collector)와 0.1µs(detector 해제)다. 초당 1,000건이면 각각 1코어의 0.02%, 0.01% 수준이다.
- 배치 크기가 감소율을 정한다: zstd 기준 1건 18%, 10건 61%, 100건 80%, 500건 83%. 1건짜리 배치 500개로 보내면 합계 121,480 → 110,737B 로 8.8% 감소에 그쳤다. 처음 측정의 4.3% 증가는 이 데이터에서는 재현되지 않았고, 배치가 없으면 이득이 거의 없다는 결론만 같다.

측정 코드는 커밋하지 않았다(일회성 벤치마크).
