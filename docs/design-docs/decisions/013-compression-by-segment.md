# 013. 배치를 먼저 모으고, 구간마다 다른 압축을 쓴다

- 날짜: 2026-08-20
- 상태: 채택

## 배경
`AgentService.publish()` 가 이벤트 한 건마다 `producer.publish()` 를 불렀다. 이 상태에서 압축만 켜면 작은 레코드를 하나씩 압축해 압축률이 나쁘고 압축 헤더 오버헤드만 붙는다.

## 결정
순서가 있는 세 단계다.

1. **발행을 배치로 모은다** (`fb53478`). 압축보다 먼저.
2. **Kafka 발행은 zstd** (`4cc8949`).
3. **에이전트 → collector 구간은 gzip** (`5ba3f22`). 서버가 요청 본문을 풀어서 받는다.

## 근거
**zstd 가 gzip 보다 큰데도 zstd 인 이유**:
> 같은 배치에서 gzip 이 11,302 바이트로 1KB 더 줄었다. 그래도 zstd 를 쓴다. detector 가 Kafka Streams 로 상시 소비해 해제 CPU 가 계속 드는데 그쪽이 zstd 가 훨씬 싸다. 1KB 차이는 그 상시 비용에 비할 것이 못 된다.

**순서가 결정이다**: 500건 배치에서 78.9% 감소였지만, 건당 발행 상태에서 같은 줄만 켰으면 **4.3% 증가**였다. 압축 헤더만 붙기 때문이다.

**에이전트 구간만 gzip 인 이유**:
> 에이전트 → collector 는 고객사 네트워크를 타는 유일한 구간인데 압축이 없다. 나머지 구간은 전부 클러스터 내부라 대역폭이 사실상 공짜다.

**압축 레벨은 기본값**:
> BestCompression 은 CPU 를 훨씬 더 쓰고 이득은 몇 %인데, EDR 에이전트가 고객 단말 CPU 를 먹는 것 자체가 문제라 여기선 기본이 맞다.

**1KB 미만은 압축하지 않는다**(`gzipMinBytes = 1024`): gzip 헤더·트레일러만 18바이트라 수백 바이트짜리 enroll·heartbeat 는 압축하면 오히려 커진다.

**서버 측 해제에 8MB 상한을 둔다**: 다른 항목은 성능 얘기지만 이건 가용성 문제다. 상한 없이 열면 인증된 에이전트 하나로 collector 를 죽일 수 있다.

**넣지 않은 것**: `gzip.Writer` 재사용(`sync.Pool`). 전송 주기가 초 단위라 할당이 병목이 아니다.

## 결과/영향
- 측정값(업링크 87.1% 감소를 8ms 로 샀다)은 측정 조건과 함께 봐야 한다.
- Protobuf 전환과 압축은 상충하지 않는다. Protobuf 는 필드명을 없애고 압축은 남은 반복을 줄인다.
