# 018. collector 가 브로커 ack 를 받고 응답하고, 실패는 503 으로 에이전트가 다시 보내게 한다

- 날짜: 2026-10-11
- 상태: 채택

## 배경
collector `EventsProducer.publish` 가 `template.send` 를 던지기만 하고 200 을 줬다. 브로커가 ack 를 못 줘도 에이전트는 성공으로 알고 배치를 지웠다. 유실이 로그 한 줄로만 남고 조용히 묻혔다(tech-debt 2026-09-23).

## 결정
- 한 요청 안의 send future 를 모았다가 **전부 보낸 뒤 한 번에** ack 를 기다린다. 상한은 5초다.
- 하나라도 실패하거나 시간을 넘기면 503 을 돌린다. 에이전트는 2xx 가 아니면 이미 배치를 버퍼 앞으로 되돌린다(`runtime.Flush`). 에이전트 코드는 바꾸지 않았다.
- 검증에서 떨어진 건은 지금처럼 `accepted` 에서 빼고 200 이다. 다시 보내도 또 떨어지므로 재전송 대상이 아니다.
- 프로듀서 `max.block.ms` 를 5초로 줄였다.

## 근거
**Outbox + CDC 를 버린 이유**: Outbox 는 DB 커밋과 발행을 함께 성공시켜야 할 때 쓴다. collector 는 이벤트를 DB 에 쓰지 않아 묶을 트랜잭션이 없다. 넣으면 초당 1,000건을 MySQL 에 먼저 쓰고 Debezium 이 다시 Kafka 로 옮기게 되어, 쓰기가 한 번 늘고 MySQL 이 새 병목이 된다. Kafka 앞에 영속 로그를 하나 더 두는 셈이다. 에이전트 버퍼가 이미 보내지 못한 이벤트를 쥐고 있으니 그것을 Outbox 로 쓴다.

**건마다가 아니라 요청 단위로 기다리는 이유**: 건마다 기다리면 `linger.ms` 배치가 안 모여 #183 압축 이득이 사라지고, 500건이면 linger 5ms 가 500번 쌓인다. 한 번에 기다리면 응답에 linger 한 번만 얹힌다.

**accepted 를 건별 결과로 바꾸지 않은 이유**: 에이전트가 accepted 를 읽고 실패분만 고르게 하려면 에이전트 배포가 필요하다. 바이너리를 바꾸면 TCC 권한이 풀리고 enroll 을 새로 탄다. 배치째 재전송은 서버만 바꿔서 된다.

**max.block.ms 를 줄인 이유**: 브로커가 죽으면 send 가 메타데이터를 기다리며 기본 60초 막힌다. 에이전트는 5초에 포기하므로 그 뒤 55초는 요청 스레드만 붙잡는다.

**graceful shutdown 은 따로 넣지 않았다**: Spring Boot 3.5 는 `server.shutdown` 기본값이 `graceful` 이다(3.4 부터). 종료 중에 끊긴 요청도 이제 2xx 를 못 받으니 에이전트가 다시 보낸다.

## 결과/영향
- **at-least-once 가 된다.** 한 배치에서 일부만 실패해도 배치 전체를 다시 보내므로 성공했던 건이 중복으로 들어간다. 중복 알림은 쿨다운이 억제하고([003](003-no-eos-suppress-at-alert.md)), ClickHouse `events` 에는 중복 행이 남는다. 브로커 장애 때만 생기는 일이라 받아들였다.
- 이벤트 응답 시간에 linger 5ms 와 브로커 왕복이 얹힌다.
- 브로커가 1대, 복제 1, 볼륨 없음이라 ack 받은 데이터도 브로커 재시작에는 사라진다. 이 결정은 그 앞단까지만 막는다.
