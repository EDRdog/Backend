# 007. 대응은 정해진 명령 종류로만 좁힌다

- 날짜: 2026-07-26
- 상태: 채택

## 배경
대응을 하려면 명령을 받아 실행하는 통로가 기기마다 있어야 한다. 이 통로는 잘못 만들면 그 자체가 백도어다.

예전에는 PowerShell 또는 sh 스크립트를 통째로 내려보내 엔드포인트가 그걸 실행했다.

## 결정
- 명령의 종류를 정해진 것으로 좁힌다. 지금 있는 것은 `kill_process` 하나이고, **서버는 대상 문자열만 보낸다.** 실제 동작은 에이전트 안의 Go 코드가 한다.
- 모르는 종류의 명령이 오면 실행하지 않고 실패로 보고한다.
- **자동으로 쏘지 않는다.** 실행 경로는 전부 만들되 대시보드에서 사람이 확인해야 실행된다.
- 격리(isolate)는 구현하지 않는다. CRITICAL 권고는 프로세스 종료로 낸다.

## 근거
스크립트를 내려보내면 플랫폼마다 문법이 달라 두 벌을 관리해야 했고, 무엇보다 **모든 엔드포인트에 임의 코드 실행 채널을 하나씩 열어 두는 셈**이었다. 수집기까지 직접 만드는 마당에 그 채널을 남길 이유가 없다.

**사람 확인을 두는 이유**: 오탐이 한 번이라도 있으면 멀쩡한 프로세스를 죽인다.

**격리를 지금 구현하지 않은 이유**(커밋 `caccb75`):
> macOS 에서 아웃바운드를 끊으면 그 기기가 서버와도 끊겨 원격 복구 수단이 사라진다. 관리 채널 예외와 자동 해제 타이머가 함께 있어야 안전하다.

**대상은 조치 시점에 다시 찾는다.** 탐지 시점의 pid 를 그대로 쓰면 그 사이 끝난 프로세스의 번호를 다른 프로세스가 받았을 수 있다. 경로 구분자가 있으면 전체 경로가, 없으면 파일명이 같아야 하고 부분 일치는 쓰지 않는다.

**안전장치**: 자기 자신과 PID 1 은 죽이지 않는다. 일부만 종료되면 성공이 아니라 `FAILED` 로 보고한다. 같은 명령을 다시 받으면 재실행하지 않고 저장된 결과만 다시 보고한다.

## 결과/영향
- 새 대응 수단은 에이전트와 서버 양쪽에 명령 종류를 추가해야 생긴다. 의도한 마찰이다.
- 격리는 미구현으로 남아 있다. `ACTION_ISOLATE` 상수는 남아 있지만 실제 동작으로 이어지지 않는다.
- 에이전트가 쓰는 상태는 `KILLED`/`NO_MATCH`/`FAILED` 뿐이다. `TIMEOUT`/`COOLDOWN`/`DISABLED` 는 엔드포인트가 판단할 수 없어 서버가 붙인다.
