# 002. 판정은 Kafka Streams 의 Processor API 로 한다

- 날짜: 2026-07-22
- 상태: 채택

## 배경
공격은 한 건으로 드러나지 않고 여러 행동의 순서로 드러난다(받아온 파일을 실행 등). 상태를 들고 판정해야 한다.

## 결정
Kafka Streams 를 서비스 프로세스 안에서 돌린다. 토폴로지는 DSL 이 아니라 **Processor API** 로 직접 쓴다. 상태는 `persistentKeyValueStore`(RocksDB) + changelog 토픽.

`selectKey` 후 `events-by-host` 내부 토픽으로 한 번 리파티션하는 단계를 **지금 필요 없는데도 유지한다.**

## 근거
**Flink·Spark 를 쓰지 않은 이유**: 잡 매니저와 워커로 이루어진 클러스터를 따로 운영해야 한다. Kafka Streams 는 라이브러리라 서비스 안에서 같이 돌고, 인스턴스를 늘리면 파티션이 자동 재분배된다.

**DSL 이 아닌 이유**: 버퍼를 앞뒤로 훑고, 상관에 쓰일 이벤트만 남기고, 윈도우 밖을 그때그때 지운다. `map`·`filter` 조합으로 표현되지 않는다.

**리파티션 유지**: README 원문 그대로다.

> 지금은 events 에 넣는 쪽이 모두 host 를 키로 쓰고 있어서 실제로 재분배가 일어나지는 않는다. 그래도 이 단계를 두는 것은 생산자가 키를 수정하거나 삭제해도 상관분석이 깨지지 않게 하기 위해서다. 대가는 내부 토픽을 한 번 거치는 지연이다.

실제로 2026-08-05 에 이것을 낭비로 보고 제거 작업을 끝까지 했다가 통째로 폐기했다. 덧붙여 rekey 를 없애보니 `DetectionTopologyTest` 2건이 깨졌다. 그 방어가 작동 중이라는 증거였다.

**워터마크를 host 별로 두는 이유**(`CorrelationProcessor`): 단말마다 전송 주기 위상이 다르다. 전역 stream-time 을 쓰면 방금 배치를 보낸 단말이 아직 주기가 안 된 단말의 이벤트를 전부 late 로 만든다.

## 결과/영향
- 내부 토픽을 한 번 거치는 지연을 지불한다.
- 판정 성능 최적화는 "판정이 안 바뀌는가"가 먼저다. 버퍼 부분 직렬화 최적화 두 갈래는 실제로 판정을 바꿔서 기각했고, 근거만 코드에 남겼다.
- 배포 직후 10분은 상태 복원과 리밸런싱이라 지연 지표를 믿으면 안 된다(`CLAUDE.md`).
