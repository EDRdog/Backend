# 012. 운영 관측은 뉴렐릭 자바 에이전트가 전부 맡는다

- 날짜: 2026-08-11
- 상태: 채택

## 배경
관측 스택(otel-lgtm)이 관측 대상과 같은 서버에 살았다.
> 서버가 죽으면 왜 죽었는지 볼 Grafana 도 같이 죽었다. 670Mi 를 쓰는 스택이 OOM 을 유발하고 그 OOM 을 설명할 데이터를 같이 날리는 구조라 사후 분석이 안 됐다.

## 결정
두 단계로 갔다.

1. (2026-08-11, `760042a`) 운영만 뉴렐릭으로 보내고 로컬은 otel-lgtm 을 그대로 쓴다. **벤더 에이전트를 붙이지 않고 기존 OTel 계측의 OTLP 엔드포인트만 바꿨다.**
2. (2026-08-11, `b5ac5fe`) 운영을 **뉴렐릭 자바 에이전트**로 바꾼다. 앱의 OTLP 는 `OTEL_ENABLED=false` 로 끈다.

벤더 API 를 쓰는 자리는 `KafkaTraceLink` 와 `TraceAttribute` 둘로 제한한다.

## 근거
1단계는 이식성을 우선했다(학생 혜택은 한시적이라 옮길 수 있어야 한다). 2단계에서 뒤집었다.
> 트레이드오프: 벤더 종속이 생긴다. 다른 백엔드로 옮기려면 6개 서비스에서 에이전트를 걷어내야 한다. #220 은 이식성을 우선했고 이번엔 관측 깊이를 택했다.

**Alloy 를 제거한 이유**: 에이전트가 로그를 직접 포워딩하므로 남겨 두면 같은 로그가 두 번 들어가 100GB 쿼터를 두 배로 태운다.

**Kafka 구간 분산추적은 껐다 켰다를 반복해 결론을 냈다.** 한 번은 "켜도 트레이스가 안 이어진다" 며 걷어냈는데, 나중에 그 판단의 근거였던 헤더 덤프가 **모듈 이름이 틀려 프로듀서 계측이 꺼져 있던 시점의 것**임을 확인하고 되살렸다. 모듈 이름에는 전체 버전 접미사가 들어가야 한다.

## 결과/영향
- **Micrometer 미터는 운영에서 한 건도 안 보인다.** 새 지표를 운영에서 보려면 미터만 넣어서는 안 되고 `TraceAttribute.number(...)` 로 트랜잭션 속성을 심어야 한다. 이걸 몰라 한 번 헛돌았다(#181).
- 관측 백엔드를 옮기려면 `KafkaTraceLink` 와 `TraceAttribute` 둘만 걷어내면 된다. 그 제한이 이 결정의 탈출구다.
- Kafka 는 서비스 맵의 노드가 될 수 없다. 맵은 프로듀서와 컨슈머를 직접 잇는다. 설정으로 바꿀 수 없다.
- 알림 조건은 배포로 반영되지 않는다. `Alerts` 워크플로를 손으로 돌려야 한다.
