# 031. 패스워드 규칙, 연속 실패 잠금, 로그인 실패 사유 비공개, 기본 패스워드 강제 변경을 api-service 의 AuthService 한곳에서 정한다

- 날짜: 2026-11-11
- 상태: 채택

## 배경
KISA EDR 성능평가 항목 BF-01.2(패스워드 보안성), BF-02(연속 인증 실패 잠금과 관리자 통보), BF-04.2(실패 사유 비공개), BF-05.1(보안정책 설정·조회), BF-08(기본 패스워드 강제 변경)이 서버 쪽에서 비어 있었다. 지금까지 가입 규칙은 8자 이상 하나였고, 로그인은 실패해도 횟수를 세지 않았고, 정책이라 부를 설정이 없었다.

## 결정

**패스워드 규칙**(`AuthValidation.passwordError`, 가입과 변경 둘 다)
- 9자 이상, 숫자·영문 대문자·영문 소문자·특수문자(영문과 숫자가 아닌 문자) 각 1개 이상.
- 계정(ID)과 같으면 안 된다. ID 가 이메일이라 이메일 전체와 `@` 앞 부분 둘 다 대소문자 구분 없이 본다.
- 같은 문자·숫자의 연속 반복은 3개 이상이면 거절한다(`aaa`, `111`). 대소문자는 다른 문자로 본다.
- 키보드상 연속은 3개 이상이면 거절한다. 줄은 숫자줄(`1234567890`), 윗줄(`qwertyuiop`), 가운뎃줄(`asdfghjkl`), 아랫줄(`zxcvbnm`), 시프트 숫자줄(`!@#$%^&*()`)이고 정방향과 역방향, 대소문자 구분 없이 본다(`qwe`, `ewq`, `123`, `321`). 알파벳 순서(`abc`)는 키보드 순서가 아니라 보지 않는다.
- 길이 기준 3 은 KISA 가 길이를 정하지 않아 우리가 고른 값이다. 4 로 올리면 `qwer` 만 막혀 `qwe` 가 통과한다. 2 로 내리면 `Hqw` 같은 흔한 조합까지 막혀 쓸 수 있는 패스워드가 지나치게 줄어든다.
- 재사용 금지는 두 선택지(직전, 3개월) 중 **직전 패스워드**를 골랐다. 변경 때 새 패스워드가 지금 패스워드와 같으면 거절한다. 3개월 이내는 이력 테이블이 필요하고 직전은 이미 있는 해시 하나로 된다.
- 패스워드 변경 API(`POST /api/auth/password`)는 현재 패스워드를 확인하고, 성공하면 감사기록 `password_change` 를 남기고, 이 세션 말고 그 유저의 다른 세션을 끊는다. 현재 패스워드가 틀리면 로그인 실패와 같이 센다. 탈취한 세션 토큰으로 이 API 를 두드려 패스워드를 알아내는 길이 잠금 없이 열려 있으면 안 된다.

**연속 실패 잠금**(BF-02)
- 계정마다 실패 횟수(`failed_logins`)와 잠금 해제 시각(`locked_until`)을 둔다. 횟수 증가와 잠금은 읽고 쓰는 대신 DB 에서 `UPDATE ... SET n = n + 1`, `UPDATE ... WHERE n >= max` 로 한다. 동시에 들어온 시도가 횟수를 덮어써 잠금을 피해 가는 길을 없애고, 잠금을 건 쪽만 통보하게 하려는 것이다.
- 횟수 max 에 닿으면 `lockMinutes` 동안 그 계정의 로그인을 막는다. 맞는 패스워드도 거부한다. 성공하면 횟수를 0 으로 돌리고, 잠기는 순간에도 0 으로 돌린다. 잠금이 풀린 뒤에는 처음부터 다시 센다.
- 잠기면 즉시 두 곳으로 알린다. 감사기록 `auth_lockout`(감사기록 조회는 admin 이 한다) 과 그 조직의 Slack webhook(`Tenant.slackWebhookUrl`, 기존 `SlackWebhookClient` 재사용). Slack 은 응답을 늦추지 않게 따로 보내고, 실패하면 경고 로그만 남긴다. 조직에 webhook 이 없으면 감사기록만 남는다.

**실패 사유 비공개**(BF-04.2)
- 없는 계정, 틀린 패스워드, 잠긴 계정은 상태코드 401, 메시지(`이메일 또는 비밀번호가 올바르지 않습니다`)가 같다. 응답 시간도 같도록 없는 계정과 잠긴 계정에도 BCrypt 비교를 한 번 한다(없는 계정은 기동 때 만든 더미 해시와 비교).
- **잠금을 알리느냐 감추느냐**는 감추기로 정했다. 잠금을 알리면 "이 이메일은 존재한다"를 알리는 것이 된다(없는 이메일은 잠기지 않으므로). 대신 사용자가 왜 안 되는지 모르는 불편이 생긴다. 이는 로그인 화면에 항상 보이는 안내 문구("연속으로 실패하면 계정이 일시 잠깁니다")와 관리자 통보로 줄인다. 안내 문구는 계정마다 달라지지 않으므로 사유 구분이 아니다.
- 남는 차이: 존재하는 계정의 실패는 DB 쓰기(횟수 증가)가 한 번 더 있어 수 밀리초 길다. BCrypt(약 100ms) 대비 작아 구분 수단으로 쓰기 어렵다고 보고 줄이지 않았다.
- 한계: 계정 단위로만 잠그므로 남의 계정을 일부러 계속 잠글 수 있다(`docs/exec-plans/tech-debt.md`).

**보안정책**(BF-05.1)
- 조직별 `security_policies` 테이블(PK tenantId, 행이 없으면 기본값). 값은 연속 실패 허용 횟수 1~5(기본 5), 잠금 분 5~1440(기본 5), 유휴 세션 종료 분 1~60(기본 10). 횟수 5 이하, 시간 5분 이상은 KISA BF-02 의 합격 조건이라 범위가 곧 그 조건이다. 유휴 상한 60 은 우리가 정했다(KISA 는 "일정 시간"이라고만 한다. 하루짜리 유휴는 정책이라 부를 수 없다).
- `GET`, `PUT /api/auth/security-policy` 는 admin 만, 범위 밖이거나 빠진 값은 400(자르지 않는다), 변경은 이전·이후 값을 담은 감사기록 `security_policy_change`. 경로를 `/api/auth` 아래에 둔 것은 이미 X-API-Key 예외라 `ApiKeyPolicy` 를 고칠 일이 없어서다.
- 정책은 `Tenant` 에 칼럼으로 더하지 않고 별도 엔티티로 뒀다. 정책 칼럼이 늘어도 tenant 의 다른 용도(webhook, enroll secret)와 섞이지 않는다.

**기본 패스워드 강제 변경**(BF-08)
- 계정에 `must_change_password` 를 둔다. 켜진 채 로그인하면 로그인 응답이 `mustChangePassword: true` 로 알리고, 그 세션은 패스워드 변경, 로그아웃, 내 정보만 된다. 나머지는 모두 403 이고 본문에 `code: "password_change_required"` 가 있어 일반 403(권한 없음)과 구분된다. `AuthService.resolve` 가 막고, 허용하는 세 곳만 `resolveAllowingPasswordChange` 를 쓴다. 모든 컨트롤러가 `resolve` 를 거치므로 컨트롤러마다 검사를 더하지 않았다.
- 가입으로 만드는 계정은 기본 패스워드가 없으므로(원문 주석) 표시를 켜지 않는다.
- **admin 이 만드는 viewer 계정**(`UserAccountService.createViewer`, `POST /api/tenant/users`)은 생성 직후 표시를 켠다. 첫 패스워드를 만든 admin 이 그 값을 알고 있어 기본 패스워드와 같은 처지이고, 그대로 두면 admin 이 viewer 의 이름으로 들어올 수 있다. 가입자(admin)가 자기 패스워드를 직접 정하는 것과 다르다. 이 API 도 패스워드 규칙(`AuthValidation.passwordError`)을 쓴다.
- 접근통제 관문(`AccessInterceptor`, ADR 033)은 `@RequiresRole` 이 붙은 모든 핸들러 앞에서 `AuthService.resolve` 를 부르므로 강제 변경, 유휴·중복 종료, 만료가 그 모든 경로에 같이 걸린다. 변경 필요 상태에서도 통과시킬 핸들러는 `@RequiresRole(allowPasswordChange = true)` 로 이름을 달아 두 곳(내 정보, 패스워드 변경)뿐이고, 로그아웃은 인증 없는 경로라 스스로 `resolveAllowingPasswordChange` 를 쓴다. `AuthSecurityIntegrationTest.forcedPasswordChangeStopsEverySessionMappingExceptTheAllowedOnes` 가 모든 세션 매핑을 훑어 이를 고정한다.

**데모 계정 예외**(사용자 결정, 2026-11-11)
- **데모 모드는 KISA 평가 범위 밖이다.** `DEMO_SEED=true` 로 만든 데모 계정(`test@edrdog.local` / `1234`)과 그 모드는 KISA 성능평가 대상이 아니며, 평가 환경에서는 `DEMO_SEED` 를 켜지 않는다. 일반 계정은 이 문서의 규칙을 그대로 따른다.
- 판별은 이메일 문자열 비교가 아니라 계정에 남는 표시 `users.demo_account` 로 한다. 이 표시를 세우는 곳은 시드(`DemoAccountSeeder`) 하나뿐이고 API 로는 못 세운다. 표시 없던 옛 시드 계정도 다음 기동 때 시드가 표시를 보장한다.
- 데모 계정에 적용하지 않는 것: 기본 패스워드 강제 변경(BF-08, 사용자 결정), 중복 접속 차단(BF-12.2, 사용자 결정. ADR 032), 연속 실패 잠금(BF-02)과 패스워드 변경. 앞의 둘은 결정이다. 뒤의 둘은 공개 데모가 깨지지 않는 쪽으로 판단했다.
  - 잠금: 패스워드가 `1234` 로 공개돼 있어 잠금이 주는 보호가 없고, 오히려 아무나 다섯 번 틀려서 데모를 막을 수 있다. 데모 계정의 실패는 세지 않는다.
  - 패스워드 변경: 공개 데모에서 누군가 바꾸면 다른 모두가 들어오지 못한다. 데모 계정의 변경 요청은 400 으로 거절한다.
- 데모 계정에도 적용하는 것: 패스워드 해시 저장과 세션 토큰 해시 저장, 유휴 종료(보는 화면은 자동 갱신이 세션을 살리고, 끊겨도 원클릭 로그인으로 바로 돌아온다), 감사기록, 로그인 실패 사유 비공개. 데모 조직(tenant 99)의 보안정책 값은 일반 조직과 같다.
- 데모 계정의 `1234` 는 패스워드 규칙을 어긴 채로 남는다. 시드가 `AuthValidation` 을 거치지 않고 저장소에 직접 넣기 때문이다(기존 동작).

## 근거
**규칙을 한 곳(`AuthValidation`)에 둔 이유**: 가입과 변경이 같은 규칙을 써야 하고 순수 함수라 표로 시험하기 쉽다.

**횟수를 메모리에 두지 않은 이유**: api-service 는 여러 대일 수 있고 재기동하면 사라진다. 계정 행이 이미 DB 에 있어 칼럼 둘이면 된다.

**버린 대안**
- 잠금을 알려 주는 응답(423 등): 위 사유로 버렸다.
- IP 단위 제한(레이트 리밋): KISA 항목이 계정 단위 잠금이고, IP 제한은 프록시 뒤에서 `getRemoteAddr` 가 장비 주소라 지금은 쓸모가 없다(ADR 028).
- `@Aspect` 나 필터로 기본 패스워드 검사: 어느 경로가 허용인지 코드에서 안 보인다. `resolve` 두 종류로 허용 경로가 이름으로 드러난다.

## 결과/영향
- 가입 규칙이 8자에서 위 규칙으로 올랐다. 이미 가입한 계정의 패스워드는 건드리지 않는다(다음에 바꿀 때 적용).
- 새 칼럼(`users.failed_logins`, `locked_until`, `must_change_password`)과 새 테이블(`security_policies`)은 `ddl-auto: update` 로 생긴다. 기존 행은 0, null, false 가 기본값이다.
- 공개 데모의 원클릭 로그인은 그대로 되고(데모 계정 예외), 여럿이 같은 계정을 써도 서로 끊기지 않는다.
- admin 이 만든 viewer 는 첫 로그인에서 패스워드를 바꿔야 한다. 프론트에 변경 화면이 없으면 그 계정은 `mustChangePassword` 를 보고도 쓸 수 없다. 로그인 응답과 내 정보가 그 상태를 알린다.
- 새 칼럼 `users.demo_account` 도 `ddl-auto: update` 로 생긴다(기본 false).
- 환경변수 추가는 없다.
