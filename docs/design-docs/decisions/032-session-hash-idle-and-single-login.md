# 032. 세션 토큰은 해시로 저장하고, 유휴 세션은 정책 시간 뒤 끊고, 같은 계정의 새 로그인이 옛 세션을 끊는다

- 날짜: 2026-11-11
- 상태: 채택

## 배경
KISA EDR-BF-03(인증 정보 재사용 방지, 선택), BF-12.1(유휴 세션 잠금·종료), BF-12.2(같은 계정 중복 접속 금지)의 서버 쪽이다. 지금까지 세션은 평문 토큰을 `sessions` 테이블의 키로 저장했고(DB 를 읽으면 살아 있는 세션을 그대로 쓸 수 있다), 만료 시각(7일)만 있었고, 한 계정이 세션을 몇 개든 가질 수 있었다.

## 결정

**토큰 해시 저장**(BF-03)
- 클라이언트가 받는 토큰은 그대로(256비트 랜덤)이고, DB 에는 SHA-256 16진수 64자만 저장한다(`Tokens.hash`). 요청이 오면 받은 토큰을 해시해서 찾는다. `sessions.token` 칼럼 이름은 기본키라 바꿀 수 없어 그대로 두고 값만 해시가 된다(엔티티 필드는 `tokenHash`).
- 로그아웃, 만료, 유휴, 중복 접속, 패스워드 변경으로 끝난 세션은 행을 지운다. 지운 토큰은 다시 만들 수 없다. 토큰이 256비트 랜덤이라 같은 값이 다시 나오지 않는다.
- 만료·유휴 판정은 행을 읽고 나서 하고, 끝난 세션은 읽은 쪽이 지운다.
- 솔트와 느린 해시(BCrypt)를 쓰지 않았다. 토큰이 이미 추측 불가능한 랜덤이라 사전 대입이 의미가 없고, 느린 해시는 요청마다 100ms 를 더한다.
- **배포 영향**: 배포 직전까지 발급된 토큰은 DB 에 평문으로 있어 해시와 맞지 않는다. 배포하면 **전원이 로그아웃되고 다시 로그인해야 한다**. 평문으로 남은 옛 행은 기동할 때 지운다(길이가 64가 아닌 행. `AuthService.purgeLegacySessions`). 그대로 두면 최대 7일 동안 DB 에서 쓸 수 있는 토큰이 남는다.

**유휴 종료**(BF-12.1)
- 세션마다 마지막 사용 시각(`last_used_at`)을 둔다. 마지막 사용 후 조직 정책의 유휴 분(기본 10)이 지났으면 그 요청이 세션을 지우고 401 로 답하고 감사기록 `session_terminate`(상세 `idle: ...`)를 남긴다.
- 사용 시각 갱신은 마지막 사용 후 1분이 지났을 때만 한다(`UserSession.TOUCH_INTERVAL`). 읽기 요청마다 DB 쓰기를 하지 않으려는 것이고, 그 결과 유휴 종료 시각은 정책 시간에서 최대 1분 어긋난다. 갱신은 `UPDATE` 쿼리로 한다. 엔티티를 `save` 하면 그사이 로그아웃으로 지워진 세션이 병합으로 되살아난다.
- 유휴 분 정책은 요청마다 읽는다(PK 조회). 캐시를 두지 않았다. 캐시를 두면 정책을 바꿔도 캐시 시간만큼 옛 값이 적용돼 "설정이 바로 적용되는가" 시험이 헷갈린다.
- 세션을 잠그는 대신 종료를 골랐다(KISA 는 둘 중 하나). 잠금 해제 화면이 따로 필요하다.
- 한계: 프론트가 화면을 열어 둔 채 주기적으로 API 를 부르면(대시보드 자동 갱신) 그 호출이 세션을 살린다. 사용자가 아무것도 안 해도 유휴가 아니게 된다. 프론트가 사람 입력이 없는 호출에는 토큰을 싣지 않거나 자동 갱신을 멈추는 것은 이 묶음 밖이다(`docs/exec-plans/tech-debt.md`). 모니터링만 하는 관리자는 유휴 종료에서 빼라는 단서(KISA 주석)도 구분할 역할이 없어 적용하지 않았다.

**중복 접속**(BF-12.2)
- 새 로그인이 성공하면 그 계정의 기존 세션을 모두 끊고 감사기록 `session_terminate`(상세 `duplicate: ...`)를 남긴다. 옛 세션은 다음 요청에서 401 이 된다.
- **끊는 쪽을 골랐다**(새 로그인 거부가 아니라). 거부하면 브라우저를 닫고 로그아웃하지 않은 사용자는 유휴 시간이 지날 때까지 못 들어오고, "이 계정은 지금 쓰는 중"이라는 사실을 패스워드를 맞힌 사람에게 알리는 것이 된다. 끊으면 정당한 사용자는 언제나 들어올 수 있다. 대가로 패스워드를 아는 사람이 정당한 세션을 끊을 수 있지만, 그 시도는 감사기록에 남고 패스워드를 아는 시점에서 이미 더 큰 문제다.
- 기준은 계정이다(KISA 는 계정 또는 권한 중 하나). 가입 시에는 세션이 없어 끊을 것이 없다.
- **데모 계정은 예외다**(사용자 결정, ADR 031 의 데모 계정 예외). 공개 데모는 같은 계정을 여럿이 쓰므로 서로 끊으면 데모가 깨진다. 데모 모드는 KISA 평가 범위 밖이다. 일반 계정에는 이 규칙이 그대로 적용된다. 유휴 종료는 데모 계정에도 적용한다.
- 중복 접속·유휴 종료는 접근통제 관문(`AccessInterceptor`, ADR 033)이 부르는 `AuthService.resolve` 안에서 걸려, `@RequiresRole` 이 붙은 모든 경로에 같이 적용된다(`AuthSecurityIntegrationTest.idleAndDuplicateEndingApplyToEverySessionMapping`).

## 근거
**버린 대안**
- 세션을 JWT 로 바꾸기: 서버가 끝낼 수 없어 유휴·중복 종료가 안 된다.
- 토큰 해시를 BCrypt 로: 위 사유.
- 유휴 시각을 매 요청 갱신: 쓰기 부하. 1분 단위로 줄여도 시험 기준(분 단위)에는 지장이 없다.

## 결과/영향
- 배포 시 전원 재로그인(위). 공개 데모의 데모 계정은 중복 접속 차단에서 빠지므로 여럿이 써도 끊기지 않는다.
- 새 칼럼 `sessions.last_used_at`(nullable)이 `ddl-auto: update` 로 생긴다.
- 환경변수 추가는 없다(`edrdog.auth.session-ttl-hours` 는 그대로).
