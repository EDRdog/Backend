# 016. 대응 명령을 DB 에 두고 kill 을 202 비동기로 바꾼다

- 날짜: 2026-09-18
- 상태: 채택

## 배경
> responder 의 명령 큐가 메모리에만 있어 재시작에 대기 명령이 사라지고, 인스턴스를 늘리면 명령을 넣은 곳과 collector 가 조회하는 곳이 어긋났다. kill 요청은 에이전트 하트비트를 기다리며 요청 스레드를 최대 30초 붙잡았다.

## 결정
- 명령을 MySQL `edrdog_responder.agent_command` 에 저장한다. 상태는 **조건부 UPDATE 로만** 바꿔 collector 가 여럿이어도 한 번만 내려간다(`PENDING` → `DELIVERED`).
- `POST /api/responder/kill` 은 명령을 저장하고 **202 와 명령 id 를 바로** 돌려준다.
- 결과는 `GET /api/responder/kill/{id}` 로 조회한다. `PENDING` 이 끝나면 대시보드가 폴링을 멈춘다.
- `TIMEOUT` 은 저장하지 않고 조회 시각으로 판단한다. 따로 두던 `ttl-ms` 는 없앴다.

## 근거
엔드포인트는 방화벽 안쪽이라 서버가 먼저 접속할 수 없다. 명령은 에이전트가 하트비트를 보낼 때 받아 간다. 그 구조에서 요청 스레드가 하트비트를 기다리면, 응답 시간이 에이전트의 하트비트 주기에 묶인다.

**메모리가 아니라 DB 인 이유**: 재시작에 대기 명령이 사라지는 것과, 인스턴스를 늘렸을 때 넣은 곳과 읽는 곳이 어긋나는 것 둘 다 조용한 고장이다.

**`TIMEOUT` 을 저장하지 않는 이유**: 저장하면 그 값을 쓰는 시점과 판단하는 시점이 갈라진다. 조회 시각으로 계산하면 한 군데서 결정된다.

## 결과/영향
- 대시보드가 폴링해야 한다. 결과가 푸시되지 않는다.
- responder 에는 앱 레벨 인증이 없다. 접근 통제는 api-service 프록시의 세션 인증과 tenant 소유 검증이 전부라, responder 를 외부에 직접 노출하면 안 된다.
- api-service 의 프록시는 비대칭으로 처리한다. 조회 실패는 502 로 올리고 kill 요청 실패는 `FAILED` 로 삼킨다. `FAILED` 로 삼키면 대시보드가 조회를 멈추고, `KILLED` 로 두면 종료되지 않은 프로세스를 완료로 넘긴다.
