# 004. 조직 구분은 서버가 node_key 로 푼다

- 날짜: 2026-07-22
- 상태: 채택

## 배경
여러 조직이 같은 백엔드를 쓴다. 이벤트에 조직 태그가 필요한데, 그 태그를 누가 정하느냐가 격리의 전부다.

## 결정
- 에이전트는 조직마다 다른 **enroll secret** 으로 등록하고 **node_key** 를 받는다. 이후 모든 요청에 `X-Node-Key` 로 싣는다.
- **엔드포인트가 보낸 조직 태그는 믿지 않는다.** 서버가 node_key 로 풀어 `tenantId` 를 덮어쓴다.
- node_key 는 평문으로 저장하지 않고 SHA-256 해시만 남긴다.
- 조회 질의의 tenant 조건은 `TenantScope` 한 군데서만 건다.

## 근거
엔드포인트는 공격자가 장악할 수 있는 기기다. 거기서 온 조직 태그를 믿으면 한 기기를 먹은 쪽이 다른 조직의 데이터에 쓸 수 있다.

**BCrypt 가 아니라 SHA-256 인 이유**: node_key 가 32바이트 SecureRandom 이라 사전공격 대상이 아니고, 매 요청 인증에 BCrypt 를 태우면 heartbeat·events 가 그만큼 느려진다.

**`TenantScope` 가 클래스로 따로 있는 이유**(주석 원문):
> 새 빌더가 격리를 다시 손으로 적지 않게 하는 것이 이 클래스의 존재 이유다. 공개 생성자나 tenant 를 안 받는 팩터리를 열면 격리가 다시 선택사항이 된다.

**멀티테넌시를 태그 배관부터 깐 이유**: 처음 도입(2026-07-22)에서는 `Event`/`Alert` 에 `tenantId` 를 추가하는 데서 멈추고 판정 로직은 건드리지 않았다. 판정은 지금도 host 기준이다.

## 결과/영향
- enroll 동시 요청이 같은 호스트의 행을 둘 만드는 레이스가 실제로 났다. 유니크 제약으로 막았다(`docs/design-docs/failures/005-*`).
- 에이전트는 서버 인증서를 고정(pinning)한다. 그래서 수집 경로에 HTTPS 가 필수고, `agent-tls` Secret 이 없으면 그 커넥터가 아예 안 열린다.
- 실패 응답은 이유를 알려주지 않는다(시크릿이 빈 값인지 틀린 값인지). 대입 시도에 힌트가 된다.
