# 026. Windows 명령행은 시스템 프로세스 프로바이더에서 받고, 에이전트는 서버 등록을 될 때까지 다시 시도한다

- 날짜: 2026-11-11
- 상태: 채택

## 배경
ADR 025 로 ETW 수집을 살린 뒤 같은 VM(Windows 11 ARM64 Pro 26300.9711, UTM, Defender 켬)에서 검증 절차를 끝까지 돌렸다. 두 가지가 남았다.

- 곧 끝나는 프로세스의 명령행이 비었다. `cmd.exe /c exit` 50건 중 1건만 인자가 실렸다. Kernel-Process ProcessStart 에는 명령행 필드가 없어서(매니페스트 v0~v4 모두) 이벤트를 받은 뒤 `NtQueryInformationProcess` 로 읽는데, 그때는 이미 프로세스가 끝나 있다. 명령행 표식을 보는 탐지(T1059 등)가 짧은 프로세스에는 걸리지 않는다.
- 부팅 직후 서버에 닿지 않으면 에이전트가 등록 실패로 바로 끝났다. 재부팅 시험에서 부팅 6초 뒤 종료 코드 1 로 끝났다. SCM 은 60초 간격으로 하루 3번만 다시 띄우므로 3분 넘게 오프라인이면 그날은 수집이 멈춘다.

## 결정
- ETW 세션을 시스템 로거 모드(`EVENT_TRACE_SYSTEM_LOGGER_MODE`)로 열고, Kernel-Process 와 함께 시스템 프로세스 프로바이더(`{151F55DC-467D-471F-83B5-5F889D46FF66}`, keyword `0x1`)를 켠다. 이 프로바이더의 Process/Start(MOF, opcode 1)에는 커널이 생성 시점에 명령행을 싣는다.
- 그 이벤트에는 실행 파일 전체 경로가 없다(`ImageFileName` 은 파일명만). 그래서 Kernel-Process 시작(전체 경로)과 같은 PID 의 시스템 프로세스 시작을 합쳐 내보낸다(`ProcessJoin`, `etw_map.go`). 어느 쪽이 먼저 와도 합친다. 짝을 2초 넘게 못 만나면 기다리지 않고 내보내고, 그때 프로세스가 살아 있으면 명령행을 `NtQueryInformationProcess` 로 읽어 채운다. 짝을 기다리던 중 프로세스가 끝나면 그때 내보낸다. 어느 경우든 시각은 시작 이벤트의 것을 쓴다.
- 시스템 로거 세션을 못 열면 일반 세션으로 열고, 시스템 프로바이더를 못 켜면 경고만 남긴다. 둘 다 예전처럼 `NtQueryInformationProcess` 로 읽는다. 프로세스 센서가 꺼져 있으면 처음부터 일반 세션을 연다.
- golang-etw 사본에 `NewSystemLoggerRealTimeSession` 을 더했다(세 번째 `EDRdog 패치`).
- 서버 등록과 첫 하트비트는 성공하거나 종료 신호가 올 때까지 5초부터 두 배씩, 최대 5분 간격으로 다시 시도한다(`cmd/edrdog-agent/retry.go`).

## 근거
같은 VM 에서 시험 프로그램으로 쟀다(레포 밖).
- 시스템 로거 세션의 Process/Start 는 `cmd.exe /c exit` 50건 모두 명령행을 실었다.
- 한 세션에 두 프로바이더를 켜면 같은 PID 의 Kernel-Process 시작이 50쌍 모두 먼저 왔다. 그래서 타이머 없이 먼저 온 쪽을 들고 있다가 합치면 된다.

버린 대안:
- **NT Kernel Logger 를 연다**: 같은 이벤트가 오지만 기기에 하나뿐이다. golang-etw 는 이미 있는 세션을 멈추고 다시 열기 때문에 다른 도구의 세션을 빼앗는다.
- **시스템 프로세스 시작만 쓴다**: 전체 경로가 없다. 명령행 첫 토큰은 만든 쪽이 넘긴 그대로라 `cmd` 처럼 경로가 빠질 수 있고, 그러면 R2/R3 룰이 보는 `\temp\` 같은 표식과 해시가 사라진다.
- **세션을 따로 연다**: 세션이 다르면 두 이벤트의 도착 순서가 보장되지 않아 기다리는 타이머가 필요하다.
- **등록 실패 시 SCM 재시작 횟수를 늘린다**: 횟수를 늘려도 상한이 있고, macOS 처럼 SCM 이 없는 곳은 그대로다.

## 결과/영향
- 같은 VM 에서 고친 에이전트로 `cmd.exe /c exit` 50건 모두 명령행이 서버까지 왔다. ARM64 빌드와 amd64 빌드(ARM64 Windows 의 x64 에뮬레이션) 둘 다 같은 결과다. 측정 조건: 위 VM, 몇 분씩 짧게 실행. 운영 실측이 아니다.
- x64 Windows Server 2025(GitHub Actions 러너, 26100, AMD64)에서도 `TestETWLive` 가 짧은 프로세스 명령행 50/50, 다섯 종 수신으로 통과했다. 이 시험을 CI 의 `agent-windows` 잡으로 PR 마다 돌린다. 서버 없이 센서까지만 본다.
- 같은 시험에서 같은 프로세스가 두 번 나간 경우는 없었다(서로 다른 명령행 50개, 행 50개).
- 터널을 닫고 띄우자 등록을 다시 시도하다가 터널을 연 뒤 다음 시도에서 등록됐다. amd64 빌드를 서비스로 깔고 서버 없이 재부팅하자 7분 넘게 같은 프로세스가 살아 있었고 SCM 실패 기록이 0건이었다.
- 합친 이벤트의 명령행 첫 토큰은 전체 경로로 바뀐다. 곧 끝나는 프로세스는 드라이브 경로를 못 구해 장치 경로(`\Device\HarddiskVolume3\...`)로 남는다.
- 시스템 로거 세션은 기기에 8개까지다. 다른 도구가 다 쓰고 있으면 일반 세션으로 열리고 명령행 보강만 빠진다.
- 짝을 잃은 시작은 최대 2초(다음 이벤트가 안 오면 다음 1분 점검까지) 늦게 나간다.
- 서버 주소나 enroll secret 이 틀려도 에이전트가 끝나지 않고 최대 5분 간격으로 경고를 남기며 다시 시도한다.
