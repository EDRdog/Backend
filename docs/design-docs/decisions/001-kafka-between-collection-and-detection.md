# 001. 수집과 판정 사이에 Kafka 를 둔다

- 날짜: 2026-07-22
- 상태: 채택

## 배경
엔드포인트가 보낸 로그를 수집 서비스가 그대로 판정기에 넘기면, 판정이 느려지거나 재시작하는 동안 수집이 같이 멈춘다. 저장까지 같은 경로에 달면 저장이 밀릴 때 판정도 밀린다.

## 결정
수집 입구는 검증한 이벤트를 `events` 토픽에 발행만 하고 끝낸다. 판정(detector)과 저장(archiver)은 **서로 다른 컨슈머 그룹**으로 같은 토픽을 각자 읽는다.

- `events`: 파티션 3, 복제 1, 파티션 키 `host`, Protobuf
- `alerts`: 파티션 3, 복제 1, 파티션 키 `host`, JSON
- 보존 기간은 기본값(7일)

## 근거
서술 원문은 `README.md` 의 "Kafka: 수집과 판정을 분리" 절에 있다. 요지는 완충, 분기, 재처리 셋이다. 룰을 고친 뒤 오프셋을 되돌려 과거 이벤트를 다시 판정할 수 있는 것이 메시지를 지우는 큐로는 안 되는 일이다.

**파티션 3**: 파티션 수가 병렬성의 상한이다. 지금은 서비스마다 인스턴스가 하나라 한 인스턴스가 3개를 다 읽지만, 부하가 늘면 코드를 고치지 않고 3대까지 늘릴 수 있다.

**파티션 키 host**: 같은 기기의 이벤트가 발행 순서대로 읽힌다. 상관분석이 기기 단위라 다른 기기와의 순서는 필요 없다.

**복제 1**: 브로커가 한 대라서다. 같은 노드에 복제해봐야 그 노드가 죽으면 같이 사라진다. 이 설정이 견디는 것은 컨슈머 장애까지이고 브로커 장애는 대비돼 있지 않다.

## 결과/영향
- **파티션 수를 나중에 바꿀 수 없다.** 늘리면 같은 host 가 다른 파티션으로 배정돼 순서 보장이 그 순간 깨진다. `AGENTS.md` 의 금지사항에 올렸다.
- 브로커 장애는 미대비 상태로 남는다. 운영 환경이라면 브로커 3대에 복제 3이 기본이다.
- 현재 Kafka 파드에 영속 볼륨이 없어 재시작하면 토픽과 `__consumer_offsets` 가 사라진다. `docs/exec-plans/tech-debt.md` 참조.
