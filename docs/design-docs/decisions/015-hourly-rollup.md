# 015. 시간 단위 롤업 테이블을 둔다

- 날짜: 2026-09-02
- 상태: 채택

## 배경
> events 는 TTL 7일인데 침해는 발각까지 몇 주가 걸린다.

7일이 지나면 "이 호스트 지난 30일 추세" 같은 질문에 답할 데이터가 아예 없다.

## 결정
INSERT 시점에 Materialized View 가 채우는 `edrdog.events_hourly`(SummingMergeTree, 180일 보관)를 둔다. 기존 질의는 그대로 두고 추세 질의만 롤업을 읽는다.

## 근거
**명분은 속도가 아니라 보존이다.** 느려서 넣은 게 아니라, 원본이 사라진 뒤에도 답할 수 있게 하려고 넣었다.

로컬 합성 200만건, 7일치, 호스트 50, 타입 4. host 하나의 7일 시간별·타입별 건수. `system.query_log` 기준.

| | read_rows | read_bytes | 소요 | 결과 행 |
|---|---:|---:|---:|---:|
| 원본 events | 65,536 | 2.19 MiB | 9ms | 338 |
| 롤업 events_hourly | 8,708 | 337.93 KiB | 4ms | 338 |

저장 크기는 9.43 MiB 대 8.15 KiB 다. 338행 중 336행이 값까지 일치하고 첫 부분 시간 한 칸만 다르다(시 단위로 접는 이상 정상).

**AggregatingMergeTree 가 아니라 SummingMergeTree 인 이유**:
> 측정이 count 하나라 countState/countMerge 가 필요 없다. 읽는 쪽이 sum(cnt) 로 끝나 SQL 을 읽는 사람이 해석할 것이 없다. uniq/quantile 이 들어오면 그때 바꾼다.

**범위를 좁힌 이유**: "최근은 원본, 이전은 롤업" 분기와 경계 이중 계산은 기존 질의를 그대로 두면 생길 자리가 없다.

**RDB 로 롤업하지 않는 이유**: 집계본을 MySQL 로 빼면 적재 경로가 하나 더 생기고 원본과 어긋날 여지가 생긴다. ClickHouse 안에서 MV 로 하면 적재 시점에 자동으로 채워진다. 상용 EDR 도 RDB 에는 테넌트·자산·상태만 두고 이벤트 조회는 컬럼 스토어를 직접 때린다.

## 결과/영향
- **이 수치도 로컬 합성 데이터다.** 운영 수치가 필요하면 같은 질의를 운영에서 다시 돌려야 한다.
- SummingMergeTree 는 병합 전 행이 남아 있어 `sum` 없이 읽으면 같은 시간이 여러 줄로 나온다. 읽는 쪽이 `sum(cnt)` 를 반드시 써야 한다.
