# 034. 에이전트 자체시험·무결성 실패는 상태가 바뀔 때만 조직 webhook 으로 알리고, 자체점검 요청자는 조직 밖에 가리고, webhook 은 DELETE 로 비운다

- 날짜: 2026-11-11
- 상태: 채택

## 배경
KISA EDR 보안 기능 자체 시험(2026-11-11, 보고서 `docs/security/kisa-security-eval-2026-11-11/README.md` 는 평가 브랜치에 있고 아직 이 브랜치에 없다. "이 시험에서 발견한 것" 절)에서 나온 세 가지를 고친다.

1. BF-10.2, BF-11.2(자체시험·무결성 실패 시 대응). 에이전트는 실패해도 감사기록 한 줄만 남기고 누구에게도 따로 알리지 않았다. 시험 맥의 에이전트는 센서가 멈춘 채 매 분 실패를 냈다.
2. 자체점검 결과(`GET /api/operations/selftest`)의 `requestedBy` 가 다른 조직 admin 의 이메일을 보여 줬다. 가입자가 전부 admin 이라 모두가 이 API 를 쓴다(ADR 029, 033 의 한계).
3. 조직 Slack webhook 은 한 번 저장하면 API 로 비울 수 없었다(null 과 빈 문자열이 400).

## 결정

### 1. 에이전트 점검 실패 통보(`AgentCheckNotifier`)
- 에이전트 감사기록을 받는 `POST /api/internal/audit` 가 저장(`recordAll`)을 마친 뒤 `AgentCheckNotifier.onRecorded` 를 부른다. 유형이 `security_check`(BF-10) 또는 `integrity_check`(BF-11)인 사건만 본다.
- (조직, host, 유형) 별로 **상태가 바뀔 때만** 보낸다. 실패 중이 아니던 키가 실패하면 "실패" 를 한 번, 실패 중이던 키가 성공하면 "회복" 을 한 번 보낸다. 같은 실패가 매 분 와도 다시 보내지 않고, 실패한 적 없는 성공은 보내지 않는다.
- 보내는 곳은 조직 webhook(`tenants.slack_webhook_url`, 계정 잠금 통보와 같은 곳)이다. webhook 이 없는 조직에는 보내지 않는다. 발송은 `CompletableFuture.runAsync` 로 따로 하고(계정 잠금 통보와 같은 방식), 어떤 예외도 밖으로 내지 않는다. 저장이 이미 끝난 뒤라 통보 실패가 감사기록을 깨지 않고, 응답이 늦어 collector 가 재전송해 기록이 중복되는 일도 없다.
- **상태는 메모리에 둔다.** 실패 중인 키만 `ConcurrentHashMap` 집합에 담는다(기기 수가 아니라 지금 실패 중인 기기 수만큼만 커진다). 재기동하면 집합이 비므로 **아직 실패 중인 기기는 다음 보고에서 "실패" 가 한 번 더 간다.** 반대로 재기동 사이에 회복한 기기의 "회복" 은 가지 않는다. 실패가 늦게 한 번 더 알려지는 쪽이라 알림이 빠지는 것보다 안전하다고 봤다.
- webhook 이 없는 동안에도 상태는 갱신한다. webhook 을 나중에 등록해도 이미 실패 중이던 기기는 다시 실패가 바뀔 때까지(회복할 때까지) 알려지지 않는다.
- 서버 자신의 자체시험·무결성 실패 통보(`SelfTestService`, `SELFTEST_WEBHOOK_URL`)는 확인만 했고 바꾸지 않았다. 이미 직전 실행과 실패 항목 집합이 달라졌을 때만 보낸다(ADR 029). 회복 통보는 없다.

### 2. 자체점검 요청자 가림
- `selftest_runs` 에 `requested_by_tenant_id` 칸을 더한다(JPA `ddl-auto: update`, null 허용). 관리자가 요청한 실행은 요청자 이메일과 조직 id 를 함께 저장한다. `SelfTestService.run` 은 이메일 문자열 대신 요청자(`Principal`, 기동·주기 실행은 null)를 받는다.
- 응답을 만들 때 조회하는 사람의 조직과 같을 때만 이메일을 준다. 다르면 "다른 조직 관리자" 를 준다. 요청자가 없는 실행(기동, 주기)은 null 그대로다.
- **이 칸이 생기기 전의 행은 조직 id 가 null 이라 모두 가린다.** 누가 요청했는지 알 길이 없어서, 보이게 두는 것보다 가리는 쪽이 안전하다. 같은 조직의 본인이 옛 요청을 못 보게 되는 것이 대가다.

### 3. webhook 비우기
- `DELETE /api/tenant/webhook`(admin, 204)과 `DELETE /api/me/webhook`(admin, 204). 개인 webhook 도 `PUT` 이 null 과 빈 문자열을 400 으로 막아 같은 문제였다. 이미 비어 있어도 204(멱등)다.
- 둘 다 감사기록 `webhook_change` 를 남긴다(대상 `tenant` 또는 `me`, 상세 `remove`, 접속 IP). webhook URL 은 URL 자체가 비밀(토큰)이라 기록에 넣지 않는다. 저장(`PUT`)에는 감사기록이 없고 이번에 더하지 않았다.
- 프론트는 이 묶음 밖이다.

## 근거
- 상태 변화 때만 보내는 이유: 에이전트는 주기마다(기본 1분) 결과를 보낸다. 그대로 알리면 센서가 멈춘 기기 한 대가 하루 1,440건의 같은 메시지를 낸다. 반대로 실패 통보만 있고 회복이 없으면 관리자가 언제 정상으로 돌아왔는지 알 수 없다.
- 상태를 DB 에 두지 않은 이유: 기기별 상태 테이블을 새로 만들면 보고마다 읽기·쓰기가 늘고, 얻는 것은 재기동 직후 알림 한 번을 아끼는 것뿐이다. 재기동은 드물고 한 번 더 알리는 쪽은 해롭지 않다.
- 버린 대안 `audit_log` 의 직전 같은 유형 기록을 읽어 상태를 구하는 방식: 상태 저장소가 따로 없고 재기동에도 맞지만, 보고마다 조회가 한 번 나간다. 기기 수가 늘면 주기 보고마다 인덱스 조회가 늘어난다. 지금 규모에서는 메모리 집합이 더 단순하다. 기기 수가 많아지거나 서버를 여러 대 띄우면(상태가 인스턴스마다 갈라진다) 이쪽으로 옮긴다.
- 요청자 가림을 응답에서만 하고 저장은 그대로 둔 이유: 같은 조직 안에서는 누가 눌렀는지가 필요하다. 조직 id 칸 하나로 충분하다.
- 조직 구분 대신 자체점검 결과 전체를 서버 운영자만 보게 하는 안: 서버 운영자 개념이 아직 없다(ADR 033, 기술부채). 이번 범위 밖이다.

## 결과/영향
- **한계**
  - 재기동하면 실패 중인 기기의 통보가 한 번 더 간다. 서버를 여러 대 띄우면 인스턴스마다 한 번씩 간다.
  - 통보 문구에 host 와 에이전트가 보낸 `detail` 이 들어간다. 에이전트가 정하는 값이다. 항목별 결과와 파일 해시만 싣고 비밀값은 없다(ADR 030).
  - 한 배치에 같은 키의 사건이 여럿이면 순서대로 센다.
  - Slack 도달은 자동 시험이 확인하지 못한다(목으로 대체). 배포 뒤 사람이 확인한다.
- **배포 때 할 일**: 조직 webhook 을 채우고, 에이전트의 점검을 일부러 실패시켜 Slack 에 "실패" 와 "회복" 이 한 번씩 오는지 본다. `selftest_runs` 새 칸은 `ddl-auto: update` 가 만든다.
