# 국정원 국가용 보안요구사항 대조 (2026-11-10)

결론: 국정원에는 EDR 전용 보안요구사항이 없다. 가장 가까운 안티바이러스제품 + 엔드포인트 공통 + 서버 공통으로 비교하면, 충족은 거의 없고 감사기록, 관리자 인증 강화, 에이전트 자체보호가 가장 크게 비어 있다. 인증(보안기능 확인서) 수준은 1인 졸업작품 범위를 넘는다. 다만 감사기록과 관리자 인증은 코드 수백 줄로 상당 부분 메울 수 있다.

## 1. 기준 문서

| 항목 | 내용 |
|---|---|
| EDR 전용 여부 | 없음(대체 기준). nis.go.kr 보안요구사항 게시판 7페이지(PP 약 70건, 3편 제품군 9개)를 전부 열어 제목을 확인했다. EDR, 엔드포인트 탐지 및 대응이라는 이름의 문서는 없다. |
| 대체 사유 | 안티바이러스제품은 악성코드 탐지 및 대응(삭제, 격리, 프로세스 종료)을 요구하고, 랜섬웨어 대응제품은 행위 기반 탐지를 요구한다. EDR이 하는 일(행위 탐지 후 프로세스 종료)에 가장 가깝다. 두 제품 모두 에이전트는 엔드포인트 공통 유형 1(가장 엄격)이고, 관리서버가 있으면 서버 공통도 같이 적용한다. |
| 문서 A | (1, 2편) 국가용 보안요구사항 V3.0 해설 및 공통보안요구사항. 2편 안에 서버 공통보안요구사항 V3.0 R1(2022.11.3)과 엔드포인트 공통보안요구사항 V3.0(2022.11.3)이 있다. 배포판 2023.8.21. https://www.nis.go.kr/AF/1_7_2_4/view.do?seq=98 (등록 2021-04-02) |
| 문서 B | (3편) 국가용 보안요구사항 V3.0 엔드포인트보안제품군. 안내문 22장 안티바이러스제품 V3.0 R1(2021.9.1), 26장 랜섬웨어 대응제품 V3.0(2023.8.21). 배포판 2023.8.21. https://www.nis.go.kr/AF/1_7_2_4/view.do?seq=105 |
| 확인 방법 | 1차 공식 문서다. PDF를 직접 받아 본문을 읽었고, 받은 파일의 SHA-512 앞부분이 게시판에 적힌 2023.8.21 배포판 해시와 일치함을 확인했다. 블로그, 기사는 근거로 쓰지 않았다. |
| 요구사항 ID | 문서의 번호를 그대로 쓴다(예: 서버 공통 7.1.1). SR-xx 같은 별도 ID는 없다. |
| 한계 | 이 PDF보다 새 개정판이 게시판에 있는지는 목록 기준(등록 2024-06-28까지)으로만 봤다. 보안기능 확인서 발급절차 안내 V2.2(2022.10.28)는 KTR 페이지가 언급만 하고 링크가 없어 읽지 못했다. 지니언스 EDR이 2022.10에 확인서를 받았다는 기사 제목은 있으나, 어느 제품 유형 기준으로 시험받았는지는 확인하지 못했다. |

## 2. 판정표

판정 기준: 충족, 부분, 미충족, 해당없음. 코드는 origin/dev 342c178 기준. KISA는 `docs/security/kisa-2021-review.md` 의 ID다. 필수/조건부는 문서 표기를 따랐고, 조건이 안 맞는 항목은 해당없음으로 뺐다.

## 3. 갭, 영향 큰 순서

1. 감사기록 전무 (서버 7.1~7.5, 엔드포인트 5.x, AV 5.1.1). 서버 공통의 필수 항목이 가장 많이 걸려 있고, 침해 사고 때 누가 어느 기기에 kill을 눌렀는지도 못 밝힌다.
   - 가장 작게 메우기: api-service에 `audit_log` 테이블 하나(시각, 사용자, tenant, 사건 유형, 대상, 결과)를 만들고 UPDATE, DELETE 코드와 API를 두지 않는다(삭제 UI 없음이 요구사항 7.3.1이다). 로그인 성공·실패, 가입, 로그아웃, kill 요청(요청자 포함), enroll을 기록하고, 조회 GET 하나만 둔다. 패스워드, 토큰은 기록하지 않는다(7.1.2).
2. 관리자 인증 강화 (서버 1.2, 1.3, 6.1, 6.2, 1.1.1 권한). 코드 수십 줄로 닫힌다.
   - 가장 작게 메우기: 로그인 실패 5회 시 5분 잠금(user 행에 카운터와 잠금 시각), 비밀번호 9자 이상과 4종 문자 검사로 `AuthValidation` 교체, 세션에 마지막 사용 시각을 두고 10분 유휴 시 만료, 새 로그인 시 이전 세션 삭제(동시 세션 제한), 가입자를 `admin`으로 고정하지 말고 `role` 검사를 최소 한 곳(kill 요청)에 건다.
3. 전송 보호와 서버 간 인증 (서버 3.1.1, 엔드포인트 1.1.1). KISA H5, H7 로 일부 보완했다.
   - 가장 작게 메우기: 운영 매니페스트의 `AGENT_TLS_ENABLED`를 true로 고정하고 코드 기본값도 true로 바꾼다. 서비스 간 내부 호출은 H5 수정에 맡긴다. 설치 스크립트 인증서 검증은 H7 수정에 맡긴다.
4. 에이전트 자체보호와 무결성 (엔드포인트 4.1, 4.2). 요구사항이 가장 높은 곳이고 현실적으로 일부만 가능하다.
   - 가능한 것: Windows 서비스 실패 시 자동 재시작, macOS LaunchDaemon `KeepAlive`, 시작할 때 자기 바이너리 SHA-256을 서버가 아는 값과 비교해 이상 시 서버에 알리기, 센서 정지 시 프로세스 종료로 서비스 재기동 유도(KISA 4-2, H8과 겹친다).
   - 어려운 것: 요구사항이 말하는 삭제 방지(OS 수준 보호), 종료 방지(커널 드라이버나 보호 프로세스)는 개인 프로젝트에서 구현하기 어렵다. 이 둘은 못 한다고 적는 것이 낫다.
5. 기본 계정, 기본 비밀번호 (서버 2.4.1). 운영에서 공개 데모 계정을 끄는 것은 KISA H4를 감수하기로 했으므로 결정 사항이다. 인증 심사 기준으로는 미충족임을 문서에 한 줄로 남긴다.
6. 에이전트 저장 비밀 보호 (엔드포인트 3.1.1). `enroll_secret` 평문 파일.
   - 가장 작게 메우기: enroll 성공 후 `enroll_secret`을 설정 파일에서 지우거나(재enroll이 필요하면 설치 링크로 다시 받는다), 안 되면 파일 권한을 root 전용으로 조인다. 키체인, DPAPI는 구현 비용이 커서 보류.
7. 에이전트 감사기록 전송 (엔드포인트 5.x). 가장 작게: 에이전트 시작, 종료, 센서 오류, 명령 결과를 기존 이벤트 채널로 `agent` 타입 이벤트로 보낸다.
8. 탐지·대응 범위 (AV 3.1.1, 랜섬웨어 2.2.1, Linux). 규칙 5개와 프로세스 종료만으로는 어느 제품 유형 기준도 맞지 않는다. 졸업작품 범위에서는 격리(파일 이동), 허용 목록 설정 화면 정도가 현실적인 한계다. Linux 센서는 별도 큰 작업이다.

## 4. 졸업작품 1인 개발이 현실적으로 할 수 있는 것과 없는 것

할 수 있는 것
- 위 갭 1, 2, 5, 7과 3의 일부. 서버 공통 7.x, 1.2, 1.3, 6.x는 코드로 닫히는 항목이라 점수가 가장 많이 오른다.
- 비교표를 근거로 한 자체 점검 문서. 확인서를 받는 것이 아니라 국가용 요구사항에 맞춰 설계했다는 설명은 가능하다.

없는 것(권하지 않는다)
- 보안기능 확인서 취득 자체. 지정 시험기관(KTR 등)의 시험을 받아야 하고, 제출물(보안기능 구현명세서, 취약점 개선 내역서, 관리 기능 목록 등)과 시험 수행이 필요하다. 개인 프로젝트로 현실적이지 않다. 유효기간은 KTR 페이지 기준 5년.
- 검증필 암호모듈(KCMVP). 서버 공통 1장 안내는 검증필 암호모듈을 탑재해야 하는 경우 암호 관련 요구사항은 그 제품의 요구사항을 따르라고 한다. 검증받은 모듈을 가져다 쓰는 것도, 직접 검증받는 것도 졸업작품 범위 밖이므로 빠른 해결책으로 권하지 않는다. 8.1.1 알고리즘 강도는 이미 문제없다는 점만 기록해 둔다.
- 요구사항 4.2.1, 4.2.3의 OS 수준 삭제, 종료 방지. 커널 모드 보호가 필요하다.
- AV 1.1.x의 시그니처 기반 파일 스캔과 전수 시험. 별도 제품이다.
- 8.4.1의 메모리 키 소거 보장. JVM, Go 런타임 제약.

## 5. 보류, 미확인 항목

- 프론트엔드 저장소(인증 입력 마스킹)와 운영 TLS 종단(ingress)은 이번 범위에서 보지 않았다.
- 운영 `AGENT_TLS_ENABLED` 값은 k8s Secret이라 확인하지 못했다.
- 서버 1.1.2 원문의 에이전트 부가속성(MAC, Serial 등) 인증 요구는 문서에서 읽었으나, 코드 쪽은 node_key 하나로 인증한다는 사실만 확인했다. 이를 부분으로 판정했다.
- 판정은 코드 정독과 grep 기준이다. 실행 시험은 하지 않았다.
