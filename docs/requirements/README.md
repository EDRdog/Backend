# 요구사항 (ERD)

ERD = Engineering Requirements Document (DB 관계도 아님). PRD(`docs/product-specs/`)를 만족하려면 무엇이 성립해야 하는지 검증 가능한 기준으로 적는다. 왜 그렇게 정했는지는 ADR(`docs/design-docs/decisions/`).

## 쓰는 법
- 기능 묶음마다 파일 하나 (`<기능>.md`), 파일 첫 줄에 PRD 기능 ID
- 기준 한 줄 = 표 한 행. ID 는 `영문2~4자-번호` (예: `UP-1`), 사람이 확인하는 기준은 `UP-M1`. 아래 예시는 검사기가 실제 기준으로 읽지 않도록 번호 대신 `N` 을 썼다
- 검증 칸은 테스트를 메서드까지 적는다: `테스트클래스.메서드` 또는 `경로::테스트이름`. 클래스 이름만 적지 않는다
- 상태 칸 값: `자동`, `자동 (환경변수 있을 때)`, `수동`, `미구현`, `일부 미구현`, `미충족`(코드가 기준과 다름), `미정`, `해당 없음`
- 구현, 배포, 삭제로 상태가 바뀌면 같은 PR 에서 고친다. `scripts/check-docs.sh` 가 상태 값과 테스트 참조를 검사한다

## 표 모양

예시는 코드블록 안에 둔다. 표로 그대로 두면 `scripts/check-docs.sh` 가 실제 기준으로 읽고 없는 테스트라며 실패한다.

```markdown
| ID | 성립해야 할 것 | 검증 | 출처 | 상태 |
|---|---|---|---|---|
| UP-N | PDF 를 받아 작업을 만든다 | `JobControllerTest.createsJob` | `docs/product-specs/service.md` F1 | 자동 |

| ID | 확인할 것 | 방법 | 상태 |
|---|---|---|---|
| UP-MN | 실제 사용자 파일을 읽는다 | 파일 3개를 올려 화면 확인 | 수동 |
```

검증 칸의 참조는 `클래스.메서드` 형식일 때만 자동 검사된다. 메서드 이름이 한글이면 검사기가 건너뛰므로, 새로 쓰는 기준은 되도록 영문 메서드를 가리킨다.
